# Совместная работа с двух компьютеров

Общий источник кода — публичный GitHub-репозиторий https://github.com/ProfessorETH/do-reliza. На каждом ПК своя копия. Локальная сеть нужна только для необязательного обмена большими ассетами; код передаём через Git.

## Подключить второй компьютер

1. Для чтения и клонирования приглашение не нужно. Для отправки своих веток принять приглашение в репозиторий под своим GitHub-аккаунтом.
2. В Codex на втором ПК открыть отдельную задачу для настройки и дать ей ссылку на репозиторий.
3. Клонировать репозиторий в новую пустую папку, например E:/release-game. Затем выбрать эту папку как проект для следующих задач.
4. Прочитать AGENTS.md, README.md и CASE-CHECK.md.
5. Убедиться, что установлены Git, Node.js (для тестов) и Python (для локального сервера). Зависимости npm устанавливать не требуется.
6. Запустить npm run check, npm test и python -m http.server 5179 --bind 127.0.0.1 из своей копии. Открыть http://127.0.0.1:5179/ на этом же ПК.

Одинаковый порт на разных компьютерах не конфликтует. localhost всегда относится к компьютеру, на котором открыт браузер. Сохранение партии также локальное.

## Одна задача — одна ветка

Перед новой задачей — чистая рабочая папка. Сохранить незавершённую работу в её ветке, затем:

```powershell
git switch main
git pull --ff-only
git switch -c feature/short-task-name
```

После изменений — проверки, просмотр diff, commit и push своей ветки, затем pull request в main. Второй участник смотрит результат и объединяет. Слияние одной задачи не должно удалять работу другой. Новые изменения из main подтягиваются после сохранения своих правок; конфликты разрешаются по смыслу, а не выбором целого чужого файла.

## Небольшие коммиты

Правило пользователя от 25 октября 2026: фиксировать законченные части постепенно, не копить всю задачу в одном большом коммите.

- Один коммит решает одну понятную задачу: например, компоновка хедера, мобильные кнопки или перемещение помощника. Связанные реализация и проверки остаются вместе.
- Перед коммитом просмотреть diff и добавить только файлы или фрагменты своей части. Чужие изменения в общих файлах не включать автоматически через `git add .`.
- Название описывает результат. В описании PR указать выполненные проверки и оставшиеся ограничения.
- Передавать законченные части через PR. При объединении сохранять полезные отдельные коммиты; не объединять независимые изменения в один коммит ради удобства.
- При синхронизации использовать fetch и fast-forward для основной ветки; изменения из main в рабочую ветку объединять с сохранением чужой работы.
- Опубликованную историю сохранять. Исправления оформлять следующими небольшими коммитами; переписывание общей истории и force-push требуют отдельной явной задачи.
- Рабочие ветки других чатов, их worktree и stash сохранять. Удалять завершённую ветку только после проверки слияния и отсутствия активного владельца.

## Предлагаемое первое разделение

### Фактические роли на 25 октября

По уточнению пользователя, разработкой занимался ProfessorETH. Участница команды уже подключена к репозиторию и готовит презентацию утром. Начальное разделение ниже остаётся историческим предложением и не подтверждает авторство выполненного кода, диалогов или ассетов. Для слайдов использовать [материалы презентации](PRESENTATION.md), указать настоящие имена участников и раскрыть применение ИИ-инструментов.

Это предложение, а не уже выданные задачи:

| Первый ПК | Второй ПК |
|---|---|
| Игровая логика, баланс, интерфейс: engine.js, app.js, style.css | Персонажи, диалоги, подготовка визуала и материалов для презентации |
| Интеграция принятых материалов в игру | Новые материалы в content/ и assets/proposals/ |

Сначала второй участник может подготовить характеры и короткие реплики шести агентов в content/characters.md, опираясь на data.js. Так работа сразу полезна и не конфликтует с интерфейсом. Менять data.js или общие файлы можно после согласования владельца задачи.
